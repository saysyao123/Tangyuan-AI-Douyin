# 当前原创 T1.1 与 Type PAL 上游的差距审查

日期：2026-10-16。结论：底座版本一致；当前成品仍属于可通关的原创短篇原型，在玩法深度、视听表现、验证覆盖与通用创作闭环方面有明显差距。继续沿用 Reforge，优先把现有短篇做扎实。

## 1. 审查对象与方法

- 上游当前 HEAD：[`IllegalCreed/type-pal@f98d0ddd89ebdee7b04502ee35de26ee82c6d246`](https://github.com/IllegalCreed/type-pal/tree/f98d0ddd89ebdee7b04502ee35de26ee82c6d246)。通过已连接 GitHub 现场读取确认，与我们的固定引擎 SHA 相同。
- 当前项目 main：[`3371f251d0bab6a865715629a88f772597c0ebd1`](https://github.com/saysyao123/Tangyuan-AI-Douyin/tree/3371f251d0bab6a865715629a88f772597c0ebd1)。审查代码为该提交内的 T1.1 构建器、适配器、补丁、网页壳和测试。
- 已发布 Site 源提交：`839a201808752111db8b269f294b53ad9659b1a3`；对照对应部署归档和可下载静态 ZIP 的实际文件库存。

## 3. 已经成立的成果

- 真正使用官方 Reforge 的世界、脚本、背包、战斗、结算和 IndexedDB 存档，未换成网页按钮驱动的独立小游戏引擎。
- NPC 接任务→跨场景→取灯芯→真实回合战斗→交物→结局闭环、跨页读档与防重复领钱已有真实浏览器证据。
- 对白快捷修改走官方 Command、session、保存事务；OPFS 工程关闭整个浏览器后重开，并在真实 Reforge 中显示修改已有证据。
- 本次发布使用原创地图/人物/怪物/运行壳贴图，并保留字体、音色与 GPL 源码下载。可继续发展自己的美术，而不是复制 PAL 商业资源。
- 失焦输入释放、显示层插值、默认轻量缓冲、加载反馈已落地，相关定向验证通过。

这些成果足以支持继续迭代。它们的验收范围仍限于现有短篇和相应场景。

## 4. 逐项差距与优化

### F01｜玩法与内容深度不足（确认，优先级高）

直接读取已交付工程：2 场景、1 名队伍成员、1 类敌人、1 个敌队、2 件物品、0 项技能；主角初始装备为空，没有商店内容。两场景地表各 1 个视觉层，碰撞网格全 0，主要靠少数装饰实体阻挡。

`tools/type_pal_t1_full.mts` 给主角 120 HP、60 attack、40 defense，雾狼 110 HP、attackStrength 0、defense 0。数值明显偏向验证流程，技能选择、装备取舍、经济和成长尚未形成玩法。不能仅凭这些字段断言雾狼完全不造成伤害，实际伤害仍由引擎公式决定。

上游已有装备、技能、队伍、成长、商店和敌人 AI 能力。应先使用这些能力做原创内容：少量互有用途的技能和道具、能够读懂的敌人招式、需要做选择的战斗，再增加伙伴、商店和升级反馈。不需要重新写战斗引擎。

验收：固定作者设计的代表战斗，实际选择技能/防御/物品，分别验证胜利、失败恢复和合理奖励；不仅靠连续空格通过。

### F02｜像素美术仍偏基础，动作语义不足（确认，优先级高）

既有截图可见：网页外壳已统一色调，但地图纹理重复、建筑和人物细节较少、战斗状态数字和图标辨识度弱。这个结论来自截图观察，不是新一轮动态视觉验收。

代码证据：`tools/type_pal_t1_art.ts` 用少量几何图形生成资源；雾狼四个朝向循环忽略方向变量；主角战斗帧主要复用同一人形和少量位移/线条；灯笼与灯芯各只有一帧。`type_pal_t1_prepare.py` 中部分状态图标共用简单斜线，基础数字采用 3×5 点阵。

优化应继续保持像素风：先做人物四向站立/行走的清楚差别、攻击/受击/防御/倒地动作、可区分的状态图标和数字，再做更丰富的驿站建筑、林地边缘与远景。环境动画应少而明确，如灯火轻摆、灯芯闪烁。素材可程序绘制或原创制作，不能以版权替换完成来代表审美完成。

验收：按原实际显示尺寸看图；四向与动作可辨；血量/状态可读；脚底、阴影、遮挡及角色尺度一致。

### F03｜音频内容未形成场景体验（确认，优先级高）

当前工程只有 `music.original-victory` 一段原创 MIDI；标题、默认战斗、普通/首领胜利四种音乐角色都指向它。驿站和雾林没有配置 scene music，雾狼 `startBattle` 显式 `music:null`，敌人 sounds 为空，工程无音效资源。

音频基础设施已有，缺的是原创场景编排与素材。应补驿站/雾林氛围、战斗/胜利的区别，以及确认、拾取、攻击、受击音效；同时提供可见的静音/音量控制并核第一次真实手势解锁。

验收：不同状态播放正确音频，出入战斗与读档恢复正确；静音、重复进入、首次播放被拒后重试无重叠与悬空错误。代码配置缺失不等于本轮已亲耳测得所有音频行为。

### F04｜平滑只覆盖队长，动作与交互边界仍需核验（代码风险）

`tools/t11/patch.py` 只将队长和相机切到 `renderedPlayerPos`；跟随者、NPC 和原有自动移动仍使用各自原路径。当前单人短篇不足以证明多人队伍同样平滑。`PresentationPosition` 的 80ms 过渡与行走帧仍为两个节拍，可能产生脚步与位移不协调。

还存在具体边界：显示器只看 scene、位移距离、height 和 enabled，不接收读档/传送原因。同场景一格以内的位置恢复会被当成普通走路插值；既有“teleport/load snap”单测覆盖的是跨场景、大位移或显式 disabled，没有覆盖这个情况。当前并未证明它导致用户可见故障。

优化：统一只读显示位置协议，显式接入 restore/teleport 的 reset；再按需要覆盖伙伴与 NPC，保留原逻辑坐标和碰撞。补拐弯、撞墙、开关菜单、交互触发、同场景相邻读档与多角色跟随的窄验证。

### F05｜性能与长稳验证范围不足（确认的证据缺口，优先级高）

既有结果：同一 headless Chromium、4× CPU throttle，旧版/新版 P95 帧回调间隔均约 16.7ms；默认缓冲由 1,024,000 降到 256,000 像素。证明减少缓冲像素及增加显示子步，没有证明整体 FPS 提升，更没有证明 CPU 降低 75%。

需要收窄此前描述：`tests/t11-stability-e2e.mjs:24` 的 12 秒/721 帧来自测试新建的 `requestAnimationFrame` 循环，只有 `frames>60` 断言，不是引擎渲染计数。浏览器继续调度帧回调时，游戏自身也可能已停；此测试不能单独证明游戏连续正常绘制。两秒移动采样也未覆盖长路线、密集实体和战斗高负载。

优化：建立与引擎更新/绘制关联的只读计数，记录输入至首次移动、首屏可玩、场景切换、P95/P99、长任务和内存趋势；在当前桌面目标下跑有动作和状态断言的长时路线，再补窄屏和不同浏览器。首轮阈值应由真实基线设定，不为过门凭空承诺所有设备 60fps。

不应重跑 P0 或单场景加载；应新增未覆盖的压力、错误和生命周期案例。

### F06｜运行中异常与存储故障恢复仍有盲区（代码风险/未实测）

当前 boot catch 能显示启动错误，但 `main.ts` 的异步 tick 在 `await frames.tick()` 成功后才调度下一帧；若异常越过内部处理边界，外层没有统一恢复流程。网页壳读旧观察快照可能继续认为 ready。这里确认的是外层保护不足，不是宣称当前已经发生崩溃。

正常快速存档已有上游串行写队列，不能把缺少按钮锁等同于存档乱序。现有压力案例证明特定输入序列能读回有效世界，但没有覆盖 quota、IndexedDB 拒绝、页面在保存途中关闭、多标签页和存储被清理。

上游也登记了[标题读档 IO 拒绝任务](https://github.com/IllegalCreed/type-pal/blob/f98d0ddd89ebdee7b04502ee35de26ee82c6d246/docs/ops/tasks/REFORGE-OPENING-LOAD-ERROR-1.md)。当前 `opening-menu.ts` 仍有 `void enterLoad()`；这是继承路径的风险，默认直进故事并不等于进入了此路径，本轮未重新运行其合法 IO 反例。

优化：对真实失败边界设计可见错误与重试，检测游戏停帧时给恢复入口；保留成功存档，区分无档/损坏/权限/空间不足。OPFS 可导出备份属于现有编辑能力，后续重点是让用户容易发现与使用，不声称原项目没有备份功能。

### F07｜发布库存混入暂存文件（确认，需优先清理）

全量盘点：CI runtime 清单共 136 文件，均在 Site 内且 SHA256 无差异；Site 的 game/editor 实际有 163 文件，额外 27 个 `assets/.rsync-tmp/` 旧 JS，共 3,825,212 字节。它们也进入同一源提交的正式部署归档和可下载静态 ZIP。

因此，“136 个已列文件一致”成立，“完整发布库存一致”没有成立。本轮没有发现活跃 HTML 引用这些临时路径，不能据此宣称正在执行旧逻辑；也不能用这个推测取消发布卫生问题。

优化：产物 staging 用干净目录；构建清单双向比较 missing/changed/extra；暂存目录一律使发布门失败；下载 ZIP、部署归档与源版本使用同一份明确文件清单。清理后只核受影响的打包/下载/启动，不重跑整套已通过故事。

### F08｜冷启动与资源体积值得专项优化（确认体积，速度收益待测）

玩家和编辑器各带一个未压缩体积 9,385,558 字节的 Unifont BDF。`bootGame` 等待 `loadGlyphs()` 后继续，字形解析为一次全表文本解析。玩家目录还同时带两个相同的 5,969,788 字节音色文件副本。磁盘冗余不等于浏览器每次会下载两份，更不能当作实测带宽。

优化方向：先记录冷/热启动实际网络与解析时间；玩家运行壳可按工程文本构造字体子集并保留兜底，编辑器保留完整创作字集；评估音色与字体路径共享、缓存和无用公共文件剔除。须保留字体/音色许可与离线资源闭包，不靠外部不稳定 CDN 换小包。

### F09｜字符串补丁与定制编辑入口脆弱（确认机制，失效为风险）

`tools/t11/patch.py` 及 prepare 脚本大量使用 `str.replace`；当前固定 SHA 已构建成功，但未逐替换断言命中次数和最终后置条件。上游源码形状变化后可能部分失配；不应未经评审自动升级 SHA。

`T1WelcomeEditor.tsx` 定位对白使用 `flow.stages[0].body[1].else[0].else[0].else[0]`，只适用于当前守灯人脚本。脚本改结构后快捷操作可能不可用或命中错误语义；现有 catch 会提示使用完整剧本编辑器，但不提供通用创作能力。

优化：先给固定补丁添加前置/后置断言，失配即停止；将对白选择改为稳定语义绑定或官方脚本选择路径。需要模块化改造时遵守 content 契约，不扩散为第二套脚本/存档。

### F10｜通用书籍制作系统尚未成立（确认，关系长期目标）

`tools/type_pal_t1_full.mts` 把《雾灯驿站》的场景、人物、坐标、任务、战斗和结局写在脚本中，不读取通用 StoryGame IR。已有 `tools/pipeline.mjs` 仍是旧 `runtime/template.html` 的独立参考运行器构建，不能把它当作已经接到 content22 的编译器。README 也明确旧运行器仅作测试夹具。

目前“原型可玩”和“换一本书能稳定产出 RPG”是两个不同验收。后续 T2 应接受稳定内容输入，输出 content22，并带来源追踪、引用/可达性校验和资源契约；至少用两部不同原创故事，只换输入包、固定同一引擎和编译器，分别构建、编辑、保存和玩到结局。无需现在先索要用户书籍。

### F11｜入口文档状态相互冲突（确认）

`WORK_T1_CONTINUE.md` 顶部已记 T1.1 通过；README 与 START_WEB 的部分当前状态段仍写 NPC、保存重开和托管未完成，最简命令仍指向旧 HTML 参考运行器。历史记录应保留，但“当前入口”不能引导后续 Agent 重复已通过阶段或跑错引擎。

优化：维护单一当前状态摘要；README/START_WEB 指向它，旧记录明确历史批次；区分已实现、已测、已发布、未覆盖。这个问题也会直接增加后续 AI 执行漂移。

## 5. 上游自身尚未完成的部分

上游当前能力地图 B5 战斗表现仍为半完成；Q1/Q2 的完整专项、A1 版本化预制库和 A8 通用独立包仍在收口范围。三阶段的云端工程/云存档/用户体系等是规划，不能作为“原项目现成有、我们漏了”的已实现能力。

我们的静态发行、原创资源和 OPFS 入口满足当前 T1 的特定场景，范围与上游通用产品路线不同；不能由此判断整体超越上游。上游数万级测试记录也不等于我们重新验证了这些用例或所有原创内容组合。

## 6. 推荐顺序与完成条件

| 顺序 | 工作包 | 可验收结果 | 本轮状态 |
|---|---|---|---|
| 1 | 发布卫生与可恢复性 | 干净全量库存；存储拒绝/停帧有可见反馈；备份入口明确；当前状态文档一致 | 已审查，未修改 |
| 2 | 流畅度与长稳证据 | 引擎关联计数；实际活动路线和边界断言；首屏/切场/P95/P99/内存记录；不改变碰撞与存档语义 | 已给窄验收目标，未新增实测 |
| 3 | 打磨一章原创 RPG | 可读 UI 与动作、不同场景音画、少量有效技能与敌人策略；如扩伙伴/装备/商店则分别完成玩法和保存闭环 | 内容建议，需按可玩效果迭代 |
| 4 | T2 可复用制作闭环 | 两份不同原创故事经同一 IR→content22 编译器产出，分别可编辑、可保存、可通关 | 尚未实现/验收 |

建议先完成 1–2，再把当前短篇打磨成能够代表平台质量的一章；不要急着扩几十张图或长篇章节。任何规模建议只是后续设计候选，不擅自改变用户已确认规则。

## 7. 本轮交付与限制

交付审查报告和机器事实，未改运行代码、未清理当前发布目录、未重新部署，也未把发现标成已修复。既有 T1 通关与编辑保存 PASS 在其原范围内继续有效。

已证实的差距：内容/音画不足、发布冗余、性能与存储验证盲区、定制构建/编辑入口的局限、通用编译未闭环和文档状态冲突。多人平滑、运行时异常停帧、相邻位置恢复等为静态风险；需要后续合法输入与代表场景的定向验证，不以猜测宣称线上故障。
